# VENT

Feedback log. Repeated/systemic workflow friction that should become future automation, docs, or workflow fixes.

## 26-08-14 07:21 — write-tag-header-trap

write tool accepts a [path#TAG] header (as its own description and the read tool's description instruct), but silently treats the literal string as the filename instead of stripping/validating the tag — creating a real file named "SKILL.md#BFE8" with no error. The refusal message ("re-read then rewrite") plus the read header display ("[SKILL.md#BFE8]") push the agent into this trap. Fix: either implement tag validation in write (parse #TAG, write to the real path, refuse on mismatch like edit does) or strip the tag with a clear notice; at minimum, document that write takes a plain path only and reject '#' in filenames.
## 26-08-17 08:45 — edit-tool-enoent-tag-format

The edit tool failed twice with ENOENT when passing the read-output tag as a path — first as `.zshrc#AD42` (relative) and then as `/home/toms/.dotfiles/.zshrc#AD42` (absolute). Only the literal bracketed header `[.zshrc#AD42]` was accepted. The guidance says "pass that whole header as the path", but the natural interpretations (bare path#tag, with or without brackets, relative or absolute) mostly fail; requiring the exact bracketed string is non-obvious and cost two failed attempts. Consider accepting path#tag without brackets, or documenting the exact expected format in the tool error message.
## 26-08-17 09:05 — path-tag-header-still-live-0.84.1

Re-tested both Aug tag-header incidents on pi 0.84.1 — the trap is still live at the edges. Current behavior matrix: write [path#CORRECT-HEX] works (stray-file bug from vent write-tag-header-trap is fixed for well-formed tags only); write [path#WRONG-HEX] succeeds WITHOUT validating the tag (tool description still claims "the tag is validated before writing" — false); write [path#NONHEX] and write path#TAG (no brackets) both silently create literal stray files, brackets included in the filename; edit path#TAG (no brackets) still fails with bare ENOENT and no format hint (vent edit-tool-enoent-tag-format unfixed). Root fixes needed upstream: one shared tag parser for read/edit/write accepting bracketed/unbracketed/relative/absolute; write must refuse tag-like paths it can't parse instead of literal-writing; ENOENT on a '#'-containing path should state the expected [path#TAG] format; response headers should warn on tag-on-tag. Until then the agent-side rule is: only verbatim-copy the full bracketed header, and ls-verify after any odd response.
## 26-08-17 10:00 — edit-tag-enoent-third-hit

Third independent hit of the edit-tag ENOENT trap, from an external complaint: agent passed the read header without brackets (repo-relative 'infra/scripts/x#0E09', then absolute) immediately after re-reading — 4 failed edit calls + 2 bash detours to verify the files existed, then plain absolute path worked instantly. Same root cause as edit-tool-enoent-tag-format and my 0.84.1 repro: brackets are mandatory literal characters, but '[path#TAG]' in the tool descriptions reads as doc-style placeholder notation, so agents strip them — three separate agents made the identical misreading. Two new costs documented beyond the failed calls: (1) bare ENOENT sends agents to bash to check file existence (format hint in the error would have saved all 4 calls); (2) behavioral erosion — agents learn 'tags cause ENOENT, plain paths work' and stop passing tags entirely, silently defeating the stale-file validation the mechanism exists for. Complaint's own proposed fix matches the pending recommendation: what read prints must round-trip through edit/write without guesswork — accept bracketed and unbracketed forms, and say so with a concrete example like [src/foo.ts#A1B2].
## 26-08-21 08:33 — stale-extension-code-in-herdr-hosts

Root-caused the auth-perms-1077 session's edit ENOENTs (vented earlier as an edit-tool bug): herdr keeps one long-lived pi host process per worktree (PID 11067 for auth-perms-1077, up since Aug 14 06:24). Extension modules are imported once per process and pinned in memory, so that host still runs the Aug-14 hashline-tools code whose unwrapHeaderPath only understands bracketed [path#TAG] — bare path#TAG fell through as a literal filename and the built-in edit failed with "Could not edit file: <path>#D422. Error code: ENOENT". The bare-tag fix has existed on disk (uncommitted) since Aug 17 and passes smoke, but the stale host never picked it up. Workaround in-session was whole-file rewrite via write + bash diff. Prevention: after editing extension code, restart affected herdr hosts (or run /reload in each) — ideally herdr would restart worktree hosts when ~/.pi/agent/extensions content changes, or pi would re-import extensions on newSession when sources changed (jiti transform cache is content-keyed, but the in-process factory cache is not invalidated).
## 26-08-31 06:03 — sourcing .zshrc for tests bypasses PATH stubs via mise

Testing functions inside ~/.dotfiles/.zshrc by sourcing it in a scratch zsh defeats PATH-based stubbing: `eval "$(mise activate zsh)"` rewrites PATH, so a stub dir placed first in PATH gets bypassed and the REAL binaries (pass-cli, ssh-agent) run — first test accidentally hit the real vault and printed real secrets into the session. Workaround for next time: don't source the whole .zshrc; extract/define just the target functions, or stub via a function wrapper (pass-cli(){ ... }) which survives PATH rewrites, and design tests to print counts/booleans, never values.
